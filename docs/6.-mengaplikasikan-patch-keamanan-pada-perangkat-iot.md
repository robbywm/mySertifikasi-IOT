## 1. Landasan Teori

### 1.1. Patch dan OTA

*Patch* adalah pembaruan firmware yang dibuat untuk menutup celah keamanan (*vulnerability*) atau memperbaiki kesalahan (*bug*). Perangkat yang sudah terpasang di lokasi klien tidak mungkin didatangi satu per satu dengan kabel USB, sehingga patch dikirim lewat OTA seperti yang sudah dipelajari pada Bab 4.

### 1.2. Empat lapisan keamanan sistem IoT

SKKNI membagi sistem keamanan IoT menjadi empat lapisan, dan tabel berikut memuat contoh pengamanan tiap lapisan pada sistem yang Anda bangun.

| Lapisan | Yang diamankan | Contoh pada pelatihan ini |
| --- | --- | --- |
| Perangkat | Firmware, memori, port fisik | Kredensial tidak ditulis di program (Bab 5), password OTA (Bab 4) |
| Jaringan | Lalu lintas data antara perangkat dan cloud | Koneksi Edgent ke Blynk Cloud memakai TLS (*Transport Layer Security*) pada port 443 |
| Platform | Akun, token, data di cloud | Auth Token unik per perangkat, pengaturan peran dan izin pengguna |
| Aplikasi | Dashboard web dan aplikasi smartphone | Login pengguna, pembatasan siapa yang boleh mengendalikan aktuator |

Menurut dokumentasinya, Blynk juga menerapkan pengamanan di sisi server. Hal itu berada di luar kendali Anda sebagai pengembang perangkat, sehingga cukup dicatat sebagai tanggung jawab penyedia platform.

### 1.3. Penempatan patch

Sebelum membuat patch, tentukan dulu lapisan tempat kelemahannya berada, karena patch firmware hanya dapat memperbaiki lapisan perangkat.

| Kelemahan | Lapisan | Bentuk perbaikan |
| --- | --- | --- |
| Layanan OTA lokal tanpa password | Perangkat | Patch firmware: tambahkan `ArduinoOTA.setPassword()` |
| Log debug menampilkan informasi sensitif di Serial | Perangkat | Patch firmware: hapus `APP_DEBUG` pada versi produksi |
| Rumus pengolahan data sensor keliru | Perangkat | Patch firmware: perbaiki rumus (studi kasus bab ini) |
| Password Wi-Fi lemah | Jaringan | Ganti password di router (di luar lingkup patch firmware) |
| Pengguna biasa dapat mengirim OTA | Platform | Ubah peran dan izin di konsol |

### 1.4. Alur uji dan penerapan patch

Patch yang salah dapat mematikan seluruh perangkat sekaligus. Karena itu, agar layanan kepada pengguna tetap berjalan, patch diterapkan secara bertahap dengan urutan berikut.

1. Kelemahan dicatat: gejala, lapisan, dan perangkat yang terdampak.
2. Patch dibuat dan nomor versi dinaikkan.
3. Patch diuji lewat USB pada perangkat uji di meja kerja.
4. Patch dikirim lewat OTA ke satu perangkat di lapangan, pada jam yang paling sedikit mengganggu pengguna.
5. Parameter keberhasilan diukur pada perangkat tersebut.
6. Jika berhasil, patch dikirim ke perangkat lain secara bertahap. Jika gagal, fallback dijalankan.
7. Hasilnya didokumentasikan.

### 1.5. Fallback

*Fallback* adalah tindakan mengembalikan perangkat ke keadaan yang berfungsi ketika patch gagal. Pada ESP8266 ada dua kemungkinan gagal, dan penanganannya berbeda.

| Jenis kegagalan | Yang terjadi | Fallback |
| --- | --- | --- |
| Unduhan terputus atau berkas rusak | Firmware baru tidak dipasang. Edgent memeriksa MD5 berkas sebelum memasangnya, dan firmware lama tetap berjalan | Kirim ulang patch setelah sinyal dan catu daya diperiksa |
| Patch terpasang tetapi berperilaku salah | ESP8266 tidak dapat kembali sendiri ke firmware lama | Kirim firmware berisi logika lama dengan nomor versi yang lebih tinggi lewat OTA. Jika perangkat tidak lagi dapat dihubungi, isi ulang lewat USB dari arsip `.bin` |

Karena itu, berkas `.bin` setiap versi yang pernah dirilis wajib diarsipkan.

### 1.6. Studi kasus: koreksi kalibrasi suhu

Praktik pada bab ini memakai skenario berikut. Anda sudah memasang puluhan perangkat di pabrik klien, lalu klien tersebut melaporkan bahwa suhu di dashboard selalu 2,5 °C lebih tinggi daripada termometer acuan pabrik. Anda membuat firmware versi 0.1.1 yang menambahkan koreksi -2,5 °C, lalu mengirimkannya lewat Blynk.Air.

{% hint style="info" %}
**Untuk pemula.** Koreksi kalibrasi sebenarnya adalah perbaikan bug, sedangkan patch keamanan menutup celah yang dapat disalahgunakan. Skenario kalibrasi dipilih karena hasilnya mudah diamati di dashboard. Alur kerjanya sama persis dengan patch keamanan: catat kelemahan, buat versi baru, uji, kirim lewat OTA, ukur, lalu dokumentasikan.
{% endhint %}

Patch lewat OTA hanya menimpa area program, sehingga konfigurasi Wi-Fi hasil provisioning pada Bab 5 tetap tersimpan dan perangkat akan langsung online lagi setelah patch terpasang.

## 3. Langkah Kerja 2: Menyiapkan Firmware Versi 0.1.0 (Sebelum Patch)

Langkah ini menyiapkan keadaan awal: perangkat berfungsi, tetapi suhu yang dikirim belum dikoreksi.

{% stepper %}
{% step %}
#### 1. Buka program [`19.PraPatching_OTA`](https://github.com/robbywm/mySertifikasi-IOT/tree/main/19.PraPatching_OTA)

Program ini adalah firmware Edgent dari Bab 5 yang ditambah pembacaan suhu DHT22 di pin D5. Isi `BLYNK_TEMPLATE_ID` dan `BLYNK_TEMPLATE_NAME` dengan milik Anda.
{% endstep %}

{% step %}
#### 2. Pastikan versinya 0.1.0

Pada baris ke-7 berkas `.ino`, pastikan `BLYNK_FIRMWARE_VERSION` bernilai `"0.1.0"`.

```cpp

// --- Tab Utama: Edgent_ESP8266 (Firmware Versi 0.1.0) ---
#define BLYNK_TEMPLATE_ID "TMPLxxxxxx"
#define BLYNK_TEMPLATE_NAME "MySertifikasi"

// VERSI AWAL: 0.1.0 (Belum Dikalibrasi Spesifik)
#define BLYNK_FIRMWARE_VERSION        "0.1.0"
#define BLYNK_PRINT Serial
#define APP_DEBUG
#define USE_KASGARIOT_SHIELD

#include "BlynkEdgent.h"
#include <DHT.h>

// Definisi DHT22 pada KasgarIoT Shield (Pin D5)
#define DHTPIN D5
#define DHTTYPE DHT22
DHT dht(DHTPIN, DHTTYPE);

BlynkTimer timer;

// Fungsi Pembacaan Sensor Suhu (Virtual Pin V0)
void kirimDataSuhu() {
  float suhuStandar = dht.readTemperature();
  
  if (isnan(suhuStandar)) {
    Serial.println("Gagal membaca dari sensor DHT!");
    return;
  }
  
  Blynk.virtualWrite(V0, suhuStandar);
  Serial.print("Versi 0.1.0 Berjalan. Suhu Standar: ");
  Serial.print(suhuStandar);
  Serial.println(" *C");
}

void setup()
{
  Serial.begin(115200);
  delay(100);
  
  dht.begin();
  BlynkEdgent.begin();
  
  // Timer mengirim data suhu setiap 2 detik
  timer.setInterval(2000L, kirimDataSuhu);
}

void loop() {
  BlynkEdgent.run();
  timer.run();
}
```

## 4. Langkah Kerja 3: Membuat Patch dan Berkas .bin

{% stepper %}
{% step %}
#### 1. Buka program [`20.Patching_OTA`](https://github.com/robbywm/mySertifikasi-IOT/tree/main/20.Patching_OTA)

Ada dua perubahan dibandingkan versi 0.1.0: nomor versi naik menjadi 0.1.1, dan suhu dikoreksi dengan `offsetKalibrasi`. Nomor versi **wajib** dinaikkan agar Blynk mengenali firmware ini sebagai versi baru. Cari `BLYNK_FIRMWARE_VERSION` (baris 7) dan `offsetKalibrasi` (baris 30) pada berkas `.ino`.

```cpp
// --- Tab Utama: Edgent_ESP8266 (Firmware Versi 0.1.1 - PATCH TERKALIBRASI) ---

#define BLYNK_TEMPLATE_ID "TMPLxxxxxx"
#define BLYNK_TEMPLATE_NAME "MySertifikasi"

// NAIKKAN VERSI FIRMWARE MENJADI 0.1.1!
#define BLYNK_FIRMWARE_VERSION        "0.1.1"
#define BLYNK_PRINT Serial
#define APP_DEBUG
#define USE_KASGARIOT_SHIELD

#include "BlynkEdgent.h"
#include <DHT.h>

#define DHTPIN D5
#define DHTTYPE DHT22
DHT dht(DHTPIN, DHTTYPE);

BlynkTimer timer;

void kirimDataSuhu() {
  float suhuStandar = dht.readTemperature();
  
  if (isnan(suhuStandar)) {
    Serial.println("Gagal membaca dari sensor DHT!");
    return;
  }
  
  // [SIMULASI PATCH] Menambahkan offset kalibrasi sebesar -2.5
  float offsetKalibrasi = -2.5; 
  float suhuTerkalibrasi = suhuStandar + offsetKalibrasi;
  
  Blynk.virtualWrite(V0, suhuTerkalibrasi);
  Serial.print("Versi 0.1.1 (Patch Terkalibrasi). Suhu Aktual: ");
  Serial.print(suhuTerkalibrasi);
  Serial.println(" *C");
}

void setup()
{
  Serial.begin(115200);
  delay(100);
  
  dht.begin();
  BlynkEdgent.begin();
  
  timer.setInterval(2000L, kirimDataSuhu);
}

void loop() {
  BlynkEdgent.run();
  timer.run();
}
```

| Parameter | Standar | Cara mengukur | Hasil | Lulus? |
| --- | --- | --- | --- | --- |
| Status pengiriman di Blynk.Air | Finished | Halaman Blynk.Air | | |
| Versi firmware di perangkat | 0.1.1 | Halaman Device Info, atau baris versi pada Serial Monitor | | |
| Perangkat kembali online | Kurang dari 3 menit sejak Start Shipping | Selisih jam yang dicatat | .... menit | |
| Fungsi yang diperbaiki | Suhu turun 2,5 °C (toleransi ±0,5 °C) dari pembacaan sebelum patch | Bandingkan nilai V0 sebelum dan sesudah | Sebelum .... °C, sesudah .... °C | |
| Fungsi lain tidak terganggu | Perangkat tetap mengirim data tiap 2 detik | Amati Chart selama 2 menit | | |

## 7. Langkah Kerja 6: Latihan Fallback

Anggaplah klien kemudian melaporkan bahwa koreksi -2,5 °C ternyata keliru untuk sebagian ruangan, sehingga patch harus ditarik.

1. Buka kembali program [`20.Patching_OTA`](https://github.com/robbywm/mySertifikasi-IOT/tree/main/20.Patching_OTA).
2. Ubah `offsetKalibrasi` menjadi `0.0`, lalu naikkan versi menjadi `"0.1.2"`. Logikanya kembali seperti versi 0.1.0, tetapi nomor versinya lebih tinggi sehingga tercatat sebagai rilis baru.
3. Buat berkas `.bin`, arsipkan, lalu kirim lewat Blynk.Air seperti pada Langkah Kerja 4.
4. Pastikan versi di perangkat menjadi 0.1.2 dan suhu kembali seperti sebelum patch.
5. Catat waktu yang dibutuhkan sejak keputusan menarik patch sampai perangkat kembali normal.

Setelah latihan selesai, kembalikan `offsetKalibrasi` ke `-2.5` dan versi ke `"0.1.1"` pada program agar sama dengan repository.
