## 1. Landasan Teori

### 1.1. Perimeter keamanan

Perimeter keamanan adalah batas yang memisahkan perangkat dari pihak yang tidak berhak, dan pada perangkat IoT batas itu memiliki dua sisi.

| Sisi | Yang dijaga | Contoh pengamanan |
| --- | --- | --- |
| Fisik | Board, port USB, tombol, memori flash | Kotak pelindung terkunci, port USB tidak terbuka untuk umum, tombol reset tidak mudah dijangkau |
| Jaringan lokal | Wi-Fi, layanan yang terbuka di perangkat | Kredensial tidak ditulis di program, jaringan IoT dipisah dari jaringan kantor, layanan OTA diberi password |

### 1.2. Gangguan, ancaman, dan model risiko

SKKNI mendefinisikan gangguan dan ancaman sebagai segala sesuatu yang berpotensi menimbulkan kejadian yang tidak diinginkan, termasuk kelemahan sistem yang dapat dimanfaatkan. Contoh yang disebut di dalam SKKNI antara lain *denial of service* dan *insufficient authorization*.

Ancaman tidak semuanya sama pentingnya, sehingga model risiko sederhana berikut dipakai untuk mengurutkannya.

**Tingkat risiko = Kemungkinan × Dampak**

| Nilai | Kemungkinan | Dampak |
| --- | --- | --- |
| 1 | Jarang terjadi | Gangguan kecil, perangkat tetap berfungsi |
| 2 | Kadang terjadi | Layanan terhenti sementara |
| 3 | Sering atau mudah terjadi | Data atau jaringan pengguna terbuka bagi pihak lain, atau layanan terhenti lama |

Hasil kali 6 sampai 9 tergolong risiko tinggi, 3 sampai 4 sedang, dan 1 sampai 2 rendah.

### 1.3. Aspek teknis dan nonteknis

SKKNI meminta analisis mencakup dua aspek. Aspek teknis menyangkut perangkat keras, jaringan, perangkat lunak, dan infrastruktur listrik, sedangkan aspek nonteknis menyangkut pembiayaan, organisasi, sumber daya manusia, hukum, dan bisnis. Contoh aspek nonteknis adalah ketiadaan petugas yang bertanggung jawab memperbarui perangkat, atau password Wi-Fi yang ditempel di dinding ruangan.

### 1.4. Kelemahan kredensial yang ditulis di dalam program

Pada Bab 3 dan Bab 4, nama dan password Wi-Fi ditulis langsung di dalam program (*hardcode*). Cara itu praktis untuk belajar, tetapi berbahaya pada produk. Siapa pun yang memegang berkas `.bin`, atau yang berhasil menyalin isi flash dari perangkat curian, dapat membaca password jaringan sebagai teks biasa. Selain itu, setiap kali password Wi-Fi berubah, firmware harus di-compile ulang untuk setiap lokasi.

### 1.5. WiFi provisioning

Dengan *WiFi provisioning*, kredensial Wi-Fi dimasukkan setelah firmware terpasang, sehingga tidak pernah ada di dalam kode program. Alurnya sebagai berikut.

1. Perangkat yang belum memiliki konfigurasi memancarkan Wi-Fi sendiri sebagai *access point*.
2. Pengguna menghubungkan smartphone ke access point itu lewat aplikasi.
3. Pengguna memilih jaringan Wi-Fi setempat dan memasukkan password-nya.
4. Perangkat menyimpan konfigurasi tersebut ke flash, lalu terhubung ke jaringan.

{% hint style="warning" %}
**Perhatian.** Provisioning mengeluarkan kredensial dari kode program dan dari berkas `.bin`. Pada Blynk Edgent untuk ESP8266, konfigurasi itu disimpan di area EEPROM tanpa enkripsi. Orang yang memegang perangkat dan mampu menyalin isi flash tetap dapat membacanya. Karena itu, pengamanan fisik tetap diperlukan.
{% endhint %}

### 1.6. Perimeter dan patch

| | Keamanan perimeter (bab ini) | Patch keamanan (Bab 6) |
| --- | --- | --- |
| Tujuan | Mencegah akses yang tidak sah | Menutup kelemahan yang ditemukan setelah perangkat beroperasi |
| Contoh | Provisioning, pemisahan jaringan, pengamanan fisik, tombol reset konfigurasi | Mengirim firmware perbaikan lewat OTA |

### 1.7. Blynk Edgent

Blynk Edgent adalah kerangka firmware dari Blynk yang sudah memuat WiFi provisioning, OTA lewat Blynk.Air, indikator LED, dan tombol reset konfigurasi. Program Edgent terdiri atas beberapa berkas (tab) yang saling terhubung.

## 5. Langkah Kerja 4: Simulasi Gangguan dan Pemulihan

Pada simulasi ini, administrator jaringan mengganti password router setelah ada dugaan peretasan, sedangkan perangkat Anda masih menyimpan password lama sehingga tiba-tiba offline. Anda harus memulihkannya tanpa laptop dan tanpa kabel data, dengan memakai tombol USER (D3) yang sudah didaftarkan sebagai tombol reset konfigurasi.

Catat waktu mulai gangguan dan waktu perangkat kembali online. Selisih keduanya adalah waktu pemulihan, yang nanti dibandingkan dengan sasaran pada rencana pemulihan.

{% stepper %}
{% step %}
#### 1. Simulasikan gangguan

Matikan router atau hotspot yang dipakai perangkat. Catat jamnya.
{% endstep %}

{% step %}
#### 2. Amati perangkat

Perangkat kehilangan koneksi. LED biru kembali berkedip singkat karena perangkat mencari jaringan yang hilang, dan status di konsol Blynk berubah menjadi Offline.
{% endstep %}

{% step %}
#### 3. Tekan dan tahan tombol D3

Tahan tombol USER tanpa dilepas.
{% endstep %}

{% step %}
#### 4. Tunggu 10 detik

Setelah kira-kira 3 detik, pola LED berubah. Setelah kira-kira 10 detik, LED berkedip rapat sebagai tanda bahwa reset konfigurasi siap dijalankan.
{% endstep %}

{% step %}
#### 5. Lepaskan tombol

Perangkat menghapus konfigurasi Wi-Fi yang tersimpan, lalu restart.

![](https://3210525233-files.gitbook.io/~/files/v0/b/gitbook-x-prod.appspot.com/o/spaces%2FOdmXmHPTecdtQ82RSbYz%2Fuploads%2FERkepkuPL3coJ478vVNZ%2Funknown.png?alt=media\&token=f326ab47-262b-404f-8a09-bb3862ac8e78)
{% endstep %}

{% step %}
#### 6. Validasi

Perangkat kembali memancarkan access point `Blynk MySertifikasi-XXXX`, dan LED biru berkedip singkat seperti pada awal provisioning.
{% endstep %}

{% step %}
#### 7. Provisioning ulang

Nyalakan kembali router atau hotspot dengan password baru, lalu ulangi Langkah Kerja 3. Catat jam ketika status perangkat kembali Online.
{% endstep %}
{% endstepper %}

Berdasarkan lembar analisis dan hasil simulasi, lengkapi rencana berikut. Sasaran waktu pemulihan seharusnya diambil dari SLA yang disepakati dengan pengguna, tetapi untuk latihan ini pakai sasaran 15 menit atau angka lain yang ditentukan instruktur.

**RENCANA PENCEGAHAN DAN PEMULIHAN**

| No | Ancaman (dari lembar analisis) | Pencegahan | Pemeriksaan berkala | Strategi pemulihan | Sasaran waktu pemulihan | Penanggung jawab |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Password Wi-Fi terbaca dari firmware | WiFi provisioning, kredensial tidak ditulis di program | Tinjau kode sebelum setiap rilis | Ganti password Wi-Fi, provisioning ulang seluruh perangkat | | |
| 2 | Firmware diganti lewat jaringan lokal | Password OTA, jaringan IoT dipisah | Periksa versi firmware di konsol setiap minggu | Isi ulang firmware resmi lewat USB dari arsip `.bin` | | |
| 3 | Perangkat offline setelah password router diganti | Tombol reset konfigurasi, prosedur pemberitahuan dari admin jaringan | Pantau status Online di konsol | Reset konfigurasi dengan tombol D3, provisioning ulang | 15 menit | |
| 4 | | | | | | |

SKKNI menyebut *backup* dan *restore* sebagai contoh strategi pemulihan. Untuk perangkat pada pelatihan ini, yang perlu dicadangkan adalah berkas `.bin` setiap versi firmware, Template ID, susunan dashboard, dan daftar perangkat beserta lokasinya.

Bandingkan waktu pemulihan hasil simulasi dengan sasaran. Jika sasaran tidak tercapai, tuliskan penyebab dan perbaikannya.
